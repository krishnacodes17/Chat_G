1.1 · Introduction

Purpose

This document defines the complete requirements for Chat-G, an AI-integrated web chat application. Registered users create conversations and interact in real time with a large-language-model assistant through a polished, responsive, theme-aware interface. The document is the single source of truth for scope across design, development, testing, and acceptance.

1.4 · Introduction

Product Scope

Chat-G is a full-stack, real-time AI chat application with the following capabilities:

  1. Authenticated accounts — register, login, logout, and session restore.
  2. Multiple independent chats with full message history per conversation.
  3. Real-time AI replies over WebSockets via the Groq LLM runtime (OpenAI fallback).
  4. Per-user daily AI request quota (default 50) with automatic midnight reset.
  5. Usage analytics — total chats, total messages, daily quota remaining.
  6. Light/dark themes, responsive layout, polished UX.
2.1 · Overall Description

Product Perspective

Chat-G is composed of two cooperating subsystems:

Backend service

Node.js + Express REST API, Socket.IO real-time layer, MongoDB (Atlas) via Mongoose, and LLM integration through LangChain adapters (Groq primary, OpenAI fallback).

Frontend application

React 19 SPA (Vite + Tailwind CSS v4) consuming the REST API and WebSocket channel. Theme-aware, responsive, keyboard-friendly.

2.5 · Overall Description

Design & Implementation Constraints

  1. Passwords must be bcrypt-hashed — never plain text.
  2. Session identity via HTTP-only cookie carrying a signed JWT.
  3. Protected routes require authUser middleware; socket handshakes validate JWT.
  4. Frontend must pass ESLint and a clean production vite build.
  5. Secrets (JWT secret, DB URI, provider keys) live only in .env.
  6. AI quota counters are database-backed, surviving restarts.

3.3 · Specific Requirements

Non-Functional Requirements

NFR-001 · Performance

AI delivery overhead beyond provider latency < 1 s over WebSockets; UI perceived latency ≤ 100 ms; route-wise code-split assets.

NFR-002 · Security

bcrypt-hashed passwords; JWT in HTTP-only cookie; auth enforced on routes & socket handshake; restricted CORS; no secrets client-side.

NFR-003 · Reliability

Provider failover (Groq → OpenAI); controllers return { success:false, message }; clean socket disconnect handling.

NFR-004 · Usability

Keyboard-first messaging, explicit loading/empty/error/limit states, toast notifications, copy affordances, sufficient contrast in both themes.

NFR-005 · Maintainability

Layered controllers / routes / models / services / sockets / utils; shared design tokens; JSDoc; ESLint-clean; zero-error build.

NFR-006 · Portability

Windows/macOS/Linux · Node ≥ 22 · all env values in .env · responsive device matrix.

NFR-007 · Availability

Managed MongoDB Atlas persistence; graceful recovery from transient DB/provider outages; readiness logged on startup.

4 · Data Requirements

Data Model & Persistence

User

  • fullName — { firstName, lastName }
  • email — unique, lowercase
  • password — bcrypt hash
  • dailyRequestCount — number (0)
  • dailyRequestDate — YYYY-MM-DD
  • createdAt / updatedAt

Chat

  • user — ObjectId → User
  • title — string
  • lastActivity — date
  • createdAt / updatedAt

Message

  • chat — ObjectId → Chat
  • user — ObjectId → User
  • content — string
  • role — user | model | system
  • createdAt / updatedAt

Persistence: MongoDB Atlas via Mongoose. Profile stats and quota are computed per request; quota counters are written to the user document so they persist across server restarts (FR-013/FR-014/FR-015).
